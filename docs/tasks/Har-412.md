# Har-412 — Allow concurrent Slack broker clients

## Finding

Personal Claude connected to the protected six-tool broker, but a fresh
ephemeral Personal Codex client reported the server unavailable. A bounded
direct bridge probe then blocked before receiving `initialize`. The broker
listener accepts one connection and serves it synchronously until EOF, so one
persistent client monopolizes the profile socket. This is deterministic and
prevents the Codex/Claude parity required by Har-403; no Slack content or tool
call occurred.

## Plan

1. Dispatch each authenticated connection to a bounded worker while retaining
   the existing peer-UID check and profile-local socket.
2. Serialize access to the shared provider and audit state without holding a
   lock while an idle client waits for input.
3. Add a focused two-client regression in which the first connection remains
   open while the second initializes and lists tools.
4. Run the complete Slack and integrated Harness gates, publish through the
   protected flow, deploy the revision-pinned service, and repeat only the
   previously non-mutating parity probes.

## Current checkpoint

The listener now admits at most eight authenticated owner connections, assigns
each to a daemon worker, and serializes only shared provider/audit handling.
Idle clients never hold that lock. A two-client regression keeps the first
connection open while the second initializes and lists tools. All 98 Slack
tests and the R3 integrated Harness gate pass on the five-path candidate. No
live service, Slack tool, content, credential, or connector was touched.

Har-412 is complete. Har-403 resumes at its separately bounded live-read gate.
