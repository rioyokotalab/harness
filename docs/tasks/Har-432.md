# Har-432 — Make validation incremental and failure-complete

## Outcome and frozen workflow

Drastically reduce routine Mac validation latency by selecting only tests owned
by the changed surface, grouping related tests into explicit tiers, and running
the complete native gate only once after every discovered issue has passed its
individual owning test. Preserve final correctness and Darwin-specific
coverage; do not hide failures, weaken assertions, or present a partial gate as
complete.

For a failure-bearing migration such as Har-428, discovery precedes repair:
collect the complete affected failure set in one keep-going pass, freeze that
set, fix one issue at a time while running only its owning test, and run no
unrelated suite during repair. After every frozen issue passes individually,
run the final complete gate once. A newly discovered final-gate failure is a
selector/discovery defect to record and repair, not a reason for an unbounded
fix-and-full-rerun loop.

The Har-428 phone checkpoint remains exactly
`ce4e9257cdc322edc25913efdfa6bb4c3c5b6aa5`. Do not contact Office or Home,
change fleet state, or start their rollout while building this workflow.

## Execution order and acceptance

1. Without running tests, inventory every validation entry point, manifest,
   selector rule, suite ownership relationship, failure mode, and historical
   Mac timing. Freeze all identified issues before editing implementation.
2. Define explicit tiers: subsecond structural checks, individual owning tests,
   subsystem groups, complete discovery, and final publication. Map every
   tracked path to the smallest sound owning set; unknown and workflow-critical
   paths must fail closed to the final tier.
3. Implement a plan/execute interface that reports selected tests and estimated
   cost before execution, supports complete keep-going failure discovery, and
   emits a machine-readable failure inventory suitable for a repair queue.
4. Fix each frozen issue with only its individual owning test. Do not run other
   suites or rerun the discovery groups after each fix.
5. Run complete native phase one exactly once on the clean final integrated
   tree, validate the selection contract, and publish through one protected PR.

Success means routine changes select a small auditable subset, affected groups
are explicit, discovery reports all failures in one pass, repair does not run
unrelated tests, final full coverage remains intact, and timing claims use
matched Riken evidence.

## Frozen static issue inventory

No test was executed during discovery. Static classification of all 1,269
tracked paths found 659 (51.9%) selecting the full gate. The proportions are
191/196 files under `tests/`, 95/98 under `libexec/`, every file under `tools/`,
`shell/`, `profiles/`, `bin/`, and `.github/`, and 20/21 under `config/`.
Only 21 distinct non-full owning suites are reachable through the current map.

The complete issue set is:

1. The broad `tests/test-*.sh` rule makes changing any owning test select all
   99 suites, so focused test maintenance is inherently full-gate work.
2. Broad lifecycle-name and directory rules similarly send almost every
   implementation path to R3 even when an exact owning suite exists.
3. `classify()` replaces every R3 suite selection with `test-phase1.sh`; the
   R3 rules that name a focused suite therefore cannot execute that suite.
4. The flat 99-suite manifest has only light/heavy scheduling classes—no
   subsystem ownership groups or group-level cost.
5. A plan reports tier and suites but not groups, per-suite estimates,
   aggregate estimated cost, or a repair order.
6. Validator execution stops at the first failing suite. It has no public
   keep-going discovery mode, so later affected failures remain hidden.
7. Failed validation publishes no machine-readable receipt. The lower-level
   runner can record failures, but phase-one cleanup removes its temporary
   receipt and logs.
8. There is no enforced single-suite repair mode; an agent cannot ask the
   validator to prove that one selected owner—and no unrelated test—ran.
9. The six-suite Darwin preflight is a separate hard-coded manifest rather than
   a tier/group view, which permits selection policy to drift.
10. The complete gate represents 1,329 estimated serial suite-seconds. The 21
    Mac/config suites alone represent 766 seconds, yet unrelated changes run
    them because R3 is both a risk label and an execution-frequency decision.
11. `test-phase1.sh` also overlaps repository-wide ShellCheck and a large
    integration fixture body with the focused pool; those gates have no
    affected-path route and therefore recur with every R3 repair attempt.
12. The hosted owner-authored PR job is skipped entirely, while weekly/manual
    events are always full. There is no protected affected-group cadence
    between those extremes.

The retained design must separate risk from frequency. Unknown or validation-
engine changes remain final-required, but they receive explicit individual
owners for repair. A complete discovery run is keep-going and occurs before
repairs; each repair invokes exactly one selected suite; the complete native
gate runs once after those individual passes.
