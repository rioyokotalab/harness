# T-360 — Correct Mac remote-control readiness detection

## Status

Phase: `complete` pending publication.

## Problem

`shared/skills/reboot-recovery/scripts/mac-reboot-state` classified the Codex
remote-control daemon pair by parentage: it counted processes named `codex` or
`codex.real` whose `ppid` was 1 and required exactly two. The pair is actually
two roles — `app-server --remote-control --listen unix://` and
`app-server daemon pid-update-loop` — and only some healthy arrangements have
both reparented to launchd. On `aist` the app-server was still a live child of
its pid-update-loop, so a fully working host reported
`remote_control=unexpected status=blocked` and reboot recovery refused to
proceed. The old rule also counted an interactive Codex TUI, which is not a
daemon, whenever one happened to be reparented.

## Change

Detect the pair by role from `ps -axo user=,args=`, restricted to the login
account: ready requires exactly one `app-server --remote-control` and exactly
one `app-server daemon pid-update-loop`, regardless of parentage. An
interactive TUI matches neither role and no longer counts.

`tests/test-reboot-recovery-skill.sh` gains a topology fixture covering
launchd-owned (ready), child-owned (ready — the case that regressed), TUI-only
(refused), missing app-server (refused), and foreign-owner (refused). The fake
`id` stub gained `-un` support, which the checker needs to bind the owner.

## Evidence

Before: `aist` `remote_control=unexpected status=blocked` while its daemon pair
had been running since 2026-07-29. After: `aist`, `riken`, and `home` all report
`remote_control=ready status=ready`; no host regressed.

`office` still reports `remote_control=unexpected` and that is correct — it has
no `codex` process at all, so remote control is genuinely not running there.
Its remedy is the documented owner step from the Mac's local Terminal:
`cd "$HOME/harness" && "$HOME/.local/bin/harness-codex" remote-control start`.

## Boundaries honored

No Mac state was changed to satisfy the checker: no daemon was started,
stopped, or reparented, no launchd definition, pairing, or SSH configuration
was touched, and no pane or transcript content was read.
