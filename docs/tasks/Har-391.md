# Har-391 — Nightly producer/consumer efficiency

## Result

The consumer protocol now includes a bounded, deterministic checkpoint planner.
It combines adjacent stages only when authority, risk, repository, and client
are identical and source access is absent. Owner choices, changed input,
ambiguity, independent review or correction, live/private sources, external
writes, and authority/risk/repository/client changes remain hard boundaries.
The planner accepts at most 32 uniquely named, schema-exact stages and returns
value-free counts without authorizing any source or write.

The same behavior and focused tests are present in the repository-onboarding
scaffold. Cold-start policy tells consumers to plan one checkpoint before
emitting intermediate reports. A protected candidate and terminal receipt may
share one publication only when one validation accepts both; independent
acceptance keeps them separate.

## Benchmark

The reproducible public fixture is
`docs/audits/har391-confirmation-efficiency.json`. For a representative
source-free plan/implement/validate/publish/receipt packet, the legacy
stage-per-report baseline is 5 confirmations, 2 consumer publications, 5
normalized latency units, and 20,480 bytes of maximum report context. The new
plan is 1 confirmation, 1 publication, 1 latency unit, and 4,096 bytes: an 80%
confirmation/critical-path/context reduction and 50% publication reduction.

With an independently reviewed correction, the result is 6 to 3 confirmations,
2 to 1 publications, and 24,576 to 12,288 context bytes. The frozen-boundary
fixture remains 13 to 13, proving the optimization adds no batching where a
gate exists. Actual historical Har-390 seconds and tokens are not claimed
because the durable public evidence does not contain those measurements.

## Validation

Focused root and onboarding-scaffold protocol suites pass. Complete Harness
