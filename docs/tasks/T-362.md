added, and no discovery link changed.

## Origin

Raised after a long Students task (T-043 Slack credential rotation) left
substantial residue that was cleaned ad hoc: a 1.5 GB build-workspace cache,
sixteen superseded owner-home transaction launchers, and sixty merged local
branches. Each cleanup was correct but improvised, and the reasoning had to be
reconstructed from scratch. The owner asked that branch removal, board
compaction, and skill-file compaction become routine rather than incidental.

Existing coverage is partial: `guarded-bulk-delete` governs the deletion
mechanism, and `docs/agent-policy/housekeeping-and-promotion.md` covers arg0
residue and guidance promotion. Neither defines a periodic routine over
repository-level residue.

## Proposed scope

Five routines, each ending in a receipt recorded in the active task record.

1. **Scratch artefact cleanup.** Build workspaces, poisoned retry directories,
   staged temporaries. Always through the `guarded-bulk-delete` plan/apply
   route. Retains provenance artifacts, reusable build inputs, and the current
   plus rollback release selections.
2. **Merged branch removal.** Classify against authoritative pull-request
   merge state, never file diffs: a stale branch differs from the trunk merely
   by being behind it, so a diff-based test misclassifies every one of them.
   Delete only branches with a merged pull request that are not checked out in
   any worktree. Record every tip SHA first so each deletion is a one-command
   restore. Never delete remote refs, rewrite history, or force-push.
3. **Superseded transaction launchers.** Owner-home staged scripts, removed by
   exact non-recursive unlink after regular-file, non-symlink, ownership, and
   single-link checks, and only when no owner command is pending. Single-file
   removal stays outside the manifest workflow by design.
4. **Board compaction.** Tighten completed rows, refresh the state summary,
   and move completed chronology into `docs/history/`, while preserving the
   resume contract and first-executable ordering. Where a repository enforces
   a cold-start context budget, the routine must verify that gate still passes
   afterwards.
5. **Stale evidence review, report-only by default.** Completed cowork
   sandboxes, seals, and preimages are surfaced as candidates and not deleted,
   because the cowork protocol prefers retaining a known sandbox over
   unreviewed cleanup.

## Out of scope

Each needs its own authority gate: anything root-owned, including staged
copies under `/run` and superseded release trees under `/opt`; credential
stores, encrypted state, and backups; historical archives, task records, and
cowork receipts; history rewriting, force-push, protected-branch settings, and
remote branch deletion; and any student or per-user directory.

## Invariants

- Read the housekeeping policy and `guarded-bulk-delete` before any
  multi-path deletion; never issue raw recursive deletion.
- Never delete anything that cannot be recomputed or restored, and record the
  restore path when deleting refs.
- Record manifest path, token, targets, verification result, and retry safety
  in the active durable ledger.
- Verify after cleanup that service selection, timers, and isolation
  boundaries are unchanged.

## Open questions for the owner

1. **Smallest surface.** The promotion policy prefers the smallest surface and
   forbids duplicating closer policy. This could be a new `shared/skills/`
   skill, or additional sections in the existing
   `housekeeping-and-promotion.md`, which already owns the housekeeping row in
   the router. A new skill is justified only if the routine is large enough to
   need its own phase router; otherwise extending the existing policy is the
   correct surface.
2. **Cross-repository consequence.** Students consumes a frozen snapshot of
   Harness shared skills and asserts an exact file count and skill set. Adding
   a skill therefore requires a coordinated re-freeze in Students; extending
   an existing policy file does not. This cost should be weighed in the
   decision above.
3. **Skill-file compaction.** The owner listed it, but the frozen snapshot in
   consuming repositories is immutable by contract, so only a repository's own
   skills are compactable, and compaction must be structural only, never
   altering a skill's semantics or authority. Whether this is worth automating
   at all is an open question; the board budget is under real pressure while
   skill size is not.
4. **Evidence deletion.** Should routine 5 ever delete, or remain report-only
   permanently?
5. **Trigger.** On task close, on a threshold such as cache size or branch
   count, or on an explicit owner request only.

## Next action

Owner decides the questions above, in particular whether this becomes a new
skill or an extension of the existing housekeeping policy. Implementation and
any discovery links follow that decision.
