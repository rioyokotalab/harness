# T-363 — Workspace lifecycle for alternating clients

## Status

Superseded by T-370 on 2026-08-01 during the owner-authorized T-369 portfolio
reset. The decision is frozen as plain per-task worktrees (option A), with no
correctness lease. T-370 owns implementation and teardown enforcement.

## Origin

The owner intends repository-native work to alternate between Codex and
Claude. Two concrete failures showed the current arrangement does not support
that safely.

In the Students repository, nine worktrees under `students-controller/` remain
for tasks whose pull requests all merged, the oldest from T-037. They pin ten
merged branches, which is the only reason those branches survived a cleanup
that removed sixty others. Worktree creation belongs to a workflow; removal
belongs to none.

In this repository, a Claude session wrote a task record and a board entry
into the shared checkout while another Claude session was working there. The
second session's commit captured both files, and it then had to publish a
separate clean branch to exclude them. Nothing was lost, but one session's
routine work silently entered another's commit.

## Diagnosis

Turn handoff is already solved. Root `AGENTS.md` makes Git and `TODO.md` the
durable source of truth and denies chat history that role, so either client
can cold-start and resume from recorded state. That machinery is sound and
should not be rebuilt.

The unsolved problem is workspace lifecycle:

- **Asymmetric workspaces.** One client works in per-task worktrees; the other
  works in place in the shared checkout. The two clients do not even collide
  in the same way.
- **No teardown.** Nothing removes a worktree when its task closes, so
  worktrees and the branches they pin accumulate indefinitely.
- **A shared mutable checkout.** Both clients may write the same working tree,
  so concurrent sessions interleave edits and commits.

No retained shared skill covers this lifecycle problem. Routine alternation
needs structural workspace isolation and should not inherit a collaboration
protocol or require a second client.

## Design principle

Isolation must be structural, not procedural. In the incident above the
session did inspect the repository before writing; the inspection was simply
minutes stale by the time it acted, because a check and a later write are
never atomic. Any rule of the form "look before writing" fails the same way. A
separate working tree cannot go stale.

## Options

**A — Per-turn worktree, symmetric.** Each task, whichever client, gets its
own worktree created from `main`; the shared checkout becomes a reference tree
pinned to `main` that neither client writes. Task close is one step: merge,
remove the worktree, delete the branch. A worktree costs about six megabytes
because the object store is shared, so isolation is effectively free.

**B — Shared checkout plus a turn lease.** One tree, plus a lease naming
client, task, host, process, and heartbeat; a client refuses to write against
a fresh foreign lease. Cheapest and matches the literal notion of taking
turns, but advisory: a client that does not consult the lease, or whose check
goes stale, still collides, and an interrupted session leaves a lease to
reclaim.

**C — A, plus a lease for observability only.** Isolation comes from separate
trees; the lease exists so the owner and both clients can see whose turn is
live and detect abandonment, with correctness never depending on it.

Recommendation: C, or plain A if less machinery is preferred. B alone repeats
the observed failure with extra steps.

## Durability

A convention nobody enforces decays; nine abandoned worktrees are the
evidence. The permanent form needs a check that runs where both clients
already run things, reporting or failing when a worktree's branch has a merged
pull request, or when the shared reference tree is dirty or off `main`. It
should not be a unit test, because it inspects live local state and would be
unreliable in hosted CI.

## Open questions

1. Design A or C.
2. Whether the convention is Harness-wide, covering every repository-native
   root, or scoped to specific repositories.
3. Where enforcement runs: a Harness native command, each repository's own
   check entry point, or the T-362 housekeeping routine.
4. Whether worktree teardown removes only clean trees, and what it does with
   untracked files a tree may still hold.

## Closeout

The nine Students worktrees cited by this diagnosis were archived and removed
under T-369 after exact merged-PR, cleanliness, ignored-cache, nested-repo,
open-file, and bundle checks. The diagnosis remains valid historical evidence;
T-370 now owns the smaller implementation: symmetric isolated worktrees,
clean reference trees, and guarded teardown integrated with housekeeping.
