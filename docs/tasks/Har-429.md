## Frozen prevention design

1. Establish one writer by replacing the standalone `resume --last` Harness
   TUI with a remote-backed TUI for the exact existing app-server thread. Use a
   distinct provisional runtime and tmux window, then promote its already-live
   pane by rename/move only after watcher, socket, thread, process, and physical
   phone acceptance. The canonical tmux geometry must not be rebuilt.
2. Do not attempt that bridge while another owner turn is active. The current
   app client must yield first; the phone agent then reconstructs solely from
   Git, `TODO.md`, this record, and live metadata.
3. Add a content-blind ownership check to the managed Codex status/monitor
   path. If one rollout is independently open through a local TUI and the
   shared app server, report `split-brain` and refuse task execution or a new
   prompt until the owner selects one continuation. A matching thread ID alone
   is never acceptance evidence.
4. Make managed Harness startup prefer an exact declared remote thread. Keep
   `--last` only for a scope proven to have one active Codex owner; never use it
   as the canonical phone/app bridge.
5. Update managed policy, recovery guidance, focused fixtures, and operator
   documentation. Validate lifecycle/safety changes with the complete phase-one
   suite before protected publication. Running clients adopt the change only
   through a deliberate bridge; publication never signals them.

If a fresh exact remote bridge again exits or cannot prove single-server
ownership, stop without retrying or retiring the phone TUI. The safe fallback
is strict separation: the phone keeps this saved root as sole writer, another
surface uses a distinct thread, and work crosses only through Git and the
Harness ledger.
