# Har-402 — Build a client-neutral Slack broker contract

## Outcome

Provide one public, secret-free broker implementation and MCP contract that
Codex and Claude can use identically through independently deployed profile
instances. Keep every repository-private profile, target, identity, and
credential outside Harness.

## Frozen design

- One broker codebase, instantiated per profile under an unprivileged service
  identity, socket, credential generation, rate-limit state, audit namespace,
  and failure domain.
- Root/systemd is credential custodian; agents receive no provider credential.
- Peer, managed-session, and repository checks contain mistakes among trusted
  same-owner agents and are not represented as hostile same-UID isolation.
- Slack payloads are untrusted context. Reads never authorize writes. A write
  requires one separately authorized frozen transaction and is never retried
  after acknowledgement or ambiguity.
- Both clients must expose identical schemas, decisions, result classes, and
  bounded failure behavior for the same profile.
- Audit data is value-free and per profile, with a default 30-day and 16-MiB
  ceiling. Content and provider identifiers never enter ordinary audit logs.

## Working set

Harness owns only generic broker code, command discovery, schema, tests, and
public deployment templates. Personal, Students, and Swallow own separate
repository-local packets and profile policy. Installed runtimes must be
revision-pinned rather than dynamically executing a Harness checkout.

## Execution stages

1. Define bounded profile/configuration and request schemas, value-free doctor,
   retry/write rules, audit contract, and client-neutral MCP surface.
2. Implement the pure broker policy core and fake-provider acceptance harness.
3. Add Codex/Claude parity, cross-profile denial, schema/scope drift, restart,
   rate-limit, write ambiguity, rotation, and rollback regressions.
4. Validate and publish the public core. Reconcile each private profile only in
   its owning repository.
5. Stop before credentials, service installation, live Slack reads, writes,
   connector revocation, or account administration. Those need separately
   recorded profile acceptance and exact owner authority.
