# Har-417 — Make Slack OAuth scope failures self-diagnosing

Har-403's first Swallow consent reached Slack's token response and then stopped
before credential installation with the generic `oauth-bot-scope-invalid`
reason. The consumed OAuth code is not retryable. Official Slack documentation
states that repeated installations add scopes and cannot downgrade an existing
installation, so the mismatch may be missing required scopes, retained extras,
or both; the current failure cannot distinguish them.

Add a bounded value-free diagnostic that reports the public missing and
additional scope names immediately before failing with a distinct stable
classification. Reject malformed or excessive provider scope sets before
printing them. Preserve exact profile scope policy, token isolation, encrypted
custody, no-retry behavior, and all credential/content non-disclosure gates.
Cover missing, additional, mixed, and malformed responses synthetically; run
the owning Slack suite and final integrated gate. Publish before one new OAuth
consent. Use the resulting diagnosis to correct only the app configuration or
installation state proven wrong, then complete one fresh changed-input consent.

Evidence: Slack's OAuth installation guide says later grants are additive and
cannot downgrade token scopes; `oauth.v2.access` returns the granted bot scopes.
Sources: `https://docs.slack.dev/authentication/installing-with-oauth/` and
`https://docs.slack.dev/reference/methods/oauth.v2.access/` (2026-08-07).

PR 730 merged the bounded diagnostic at `8861c54`. It identified no missing
scope and exactly one retained write scope. The owner removed the stale Slack
installation and completed one fresh consent; the replacement encrypted
Swallow bundle passed exact-scope validation. No credential or Slack content
was exposed, read, or persisted outside its declared encrypted store. Har-417
is complete.
