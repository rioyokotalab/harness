# Initial plan

## Confirmed facts and assumptions

Confirmed:

- Harness and Website are public; Students and Swallow are private.
- Recent private run lower bounds are 500 Students runs in less than a day and
  279 Swallow runs over five days.
- Current private CI runs for both pull requests and the identical merged
  `main` tree.  Students also runs its boundary job on owner pull requests.
- Required approval count is zero and must remain unchanged.
- A matched duration start requires 84,100 words across root policy, the
  9,199-line board, selected skills/references, and skill-creator guidance.
- The clean complete Harness suite is approximately two minutes; many
  unrelated focused suites are below one second while several Mac fixtures
  take 26–34 seconds.
- GitHub documents that a job-level conditional skip reports success even when
  required, while workflow-level/path skips can remain pending.
- GitHub documents no billable minutes for public standard-hosted or
  self-hosted jobs, but warns against persistent self-hosted runners for
  untrusted pull-request code.

Assumptions to falsify:

- one protected PR per coherent task and removal of duplicate `main` runs
  preserve sufficient durable publication;
- trusted owner changes can use exact-tree local evidence while job-level
  skips preserve existing required contexts without hosting administration;
- conditional skill references and an indexed historical ledger preserve all
  task capabilities;
- changed-path impact selection can safely escalate unknown/high-risk changes
  while avoiding unrelated suites;
- ordinary repository work is already target-isolated enough that only policy,
  receipt, and test-root changes are needed.

## Steps

1. Measure Actions frequency, context size, clean validation latency, and
   lock/worktree topology on the immutable baseline.
2. Independently challenge the benchmark and proposed architecture in both
   clients; seal and import Claude's result.
3. Reciprocally critique the strongest contrary findings and freeze retained
   changes.
4. Implement in the target only: compact/index the ledger, slim skill entry
   points with conditional references, add impact-selected exact-tree
   validation/receipts, clarify one-PR publication, and remove private
   owner-run duplication without weakening untrusted jobs.
5. Validate B1–B6, keep/revert each iteration, and publish one coherent
   protected change per repository without touching live project work.
6. Clean only task-owned and independently eligible residue with guarded
   deletion; finish the 11 time slices and fleet-health handoff at 09:00 JST.

## Evidence questions

- Which runs actually consume the private allowance, and what is the minimum
  sustainable repository-only design?
- Which text is truly mandatory for each task scenario, and can a deterministic
  router select every applicable gate without broad preload?
- What task history is necessary at cold resume versus searchable archive?
- Which test owns each changed component, and which changes must always run the
  complete suite?
- Does any normal Harness/Students/Swallow operation share a mutable lock,
  temporary root, receipt, branch, or lifecycle action?
- Can an untrusted pull request still trigger hosted CI and Students boundary
  enforcement after owner-only optimization?
- What evidence would falsify the claimed autonomy or speed improvement?

## Risks and recovery

Job-level skips could convert required CI into an unaudited owner bypass;
mitigate with exact-tree local receipts and preserve hosted checks for
non-owner changes.  An overaggressive router could omit a safety gate; fail
closed on unknown mappings and test all benchmark scenarios.  Ledger
compaction could hide owner decisions; move bytes without rewriting them and
retain an indexed provenance pointer.  Validation caches can go stale; bind
receipts to tree, validator version, selected test manifest, platform, and
result.  Parallel tests can collide; use unique roots and target-scoped locks.
Any ambiguous external state, failed safety fixture, protected-file seal
change, or live-session impact stops that mutation.  Git restores a reverted
candidate; guarded deletion handles task-owned trees.
